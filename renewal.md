# Epoch Renewal Protocol

Use this file only after the first 120 bundles are complete, retired, or explicitly carried forward, or when a human formally ends the epoch.

The goal is to create the next ten-year pipeline from fresh evidence. The 2026–2036 plan is a structural example, not a prophecy to photocopy.

## Required evidence packet

Collect:

- current `main` commit and release,
- active routes, manifests, servers, service workers, schemas, migrations, and compatibility register,
- current product screenshots for every golden-path stage,
- redacted user feedback themes,
- incident and recovery history,
- accessibility, boot, storage, sync, export, and reliability measurements,
- protocol and dependency support horizons,
- active community, operator, and extension practices,
- completed, retired, failed, and repeatedly deferred bundles,
- first-decade retrospective,
- unresolved data-preservation obligations.

When screenshots or feedback are unavailable, continue with repository and incident evidence but mark the gap. Do not invent adoption, satisfaction, or product success.

## Renewal steps

1. Freeze the old epoch checklist.
2. Archive its plan, imprint, rebase history, and retrospective under a dated read-only directory.
3. Create a new epoch identifier and a new snapshot commit.
4. Write a new fresh imprint without copying old route assumptions.
5. Define the product invariants that still survive.
6. Identify the largest current risks and duplicate owners.
7. Detail the first four quarters.
8. Define years two and three at bundle depth.
9. Define years four through ten as directional arcs with compatibility, preservation, and rebase obligations.
10. Schedule at least annual rebases.
11. Include an end-of-epoch renewal bundle.
12. Generate a new ordered Markdown checklist and fresh epoch header.
13. Update `AGENTS.md` to point to the active epoch.
14. Verify every named path and current repository check.
15. Require human approval before the new checklist becomes active.

## Renewal quality gates

The next plan must:

- begin from a real commit,
- preserve user-owned data and exports,
- preserve a usable local-first path,
- name what should be deleted as well as what should be built,
- distinguish product goals from technology guesses,
- avoid duplicating current open pull requests,
- contain one-bundle-per-PR boundaries,
- keep agents outside merge authority,
- include rebase and emergency-stop procedures,
- remain useful when hosted AI is absent.

## Fallback generation prompt

```text
Read the archived epoch, its retrospective, the current AGENTS.md, the fresh imprint,
the compatibility register, current screenshots, redacted feedback themes, incident reports,
and current repository checks.

Create a new ten-year Commonweave pipeline.
Use the archived pipeline only as a structural example.
Treat current executable code and user evidence as the source of truth.
Detail the first four quarters, keep later years adaptive, schedule annual rebases,
preserve local-first operation and user-owned data, and require one bundle per draft pull request.
Do not grant agents merge authority.
Mark every evidence gap and uncertainty.
```

The generated plan is a proposal until a human activates it.
